# SPEC 2.0 — Components 1:1 (JSX components → native Elementor components)

Status: SPECCED (source-verified against Elementor 4.2.1 free + editor JS). Owner: TBD.
All wire formats below were extracted from plugin source with file:line references
recorded in the research log (session 2026-08-12). Verify against target Elementor
version before implementation begins.

## What it unlocks

Today `<Card/>` used 10× compiles to 10 disconnected trees; editing one in the
editor orphans the other nine. After 2.0, an exported JSX component compiles to a
**registered Elementor component** (dedicated `elementor_component` CPT document)
and every invocation emits a native `e-component` instance whose JSX props map to
Elementor **overridable props** — the editor shows them as labeled controls,
grouped, on every instance; editing the component updates all instances. Agent
output stops being "a page" and becomes "a design system the client keeps."

## Native model (contract with Elementor — verified 4.2.1)

1. Component = full document on CPT `elementor_component`; tree in `_elementor_data`;
   registry meta `_elementor_component_uid` (client-generated) and
   `_elementor_component_overridable_props` `{props:{<key>:{overrideKey,label,elementId,
   propKey,elType,widgetType,originValue,groupId}},groups:{items,order}}`.
2. Overridability is universal-by-union: every atomic settings prop accepts the
   `{"$$type":"overridable","value":{"override_key","origin_value"}}` envelope —
   EXCEPT `classes` (explicitly excluded). **Styles cannot be overridden. Period.**
3. Instance node:
   `{elType:"widget", widgetType:"e-component",
     settings:{component_instance:{$$type:"component-instance",
       value:{component_id:{$$type:"number",value:<id>},
              overrides:{$$type:"overrides",value:[
                {"$$type":"override","value":{override_key,override_value,
                  schema_source:{type:"component",id:<same id>}}}]}}}},
     editor_settings:{component_uid}, elements:[]}`
   Invariants: every override's `schema_source.id` === `component_id` (else whole
   prop rejected); unknown override_keys silently dropped; `override_value:null`
   = explicit clear. Nested re-exposure = `overridable`-wrapping-`override`.
4. REST: `elementor/v1/components` — POST create (batch items `{uid,title(2..200),
   elements,settings}`, `status: publish|draft`; autosave coerced to draft),
   `create-validate` dry-run twin, GET list/styles/overridable-props,
   PUT status (publish only), lock/unlock/lock-status, archive, update-titles.
   422 codes to handle: `components_validation_failed`,
   `circular_dependency_detected`, `non_atomic_element_in_component`,
   `settings_validation_failed`.
5. Hard limits: ≤100 components/site; unique title+uid; atomic-only trees
   (**no `html` widget inside a component** — exjsx runtime carrier, navBar,
   browserMock are non-registrable); no cycles (DFS, depth 50, uid-aware for
   same-batch); title ≥2 chars.
6. Gating: module ON by default on fresh 4.x (`e_components` + `e_atomic_elements`);
   **create/rename/archive/add-to-page need ACTIVE Elementor Pro** (REST access
   controller); publish/edit/lock accept expired Pro. Locks are 1h editor-courtesy
   post-meta — REST saves are NOT blocked by them; polite writers check
   `lock-status` first.
7. Frontend inner-element ids: djb2-33/base36 hash of `instanceId+'_'+originId`
   path, last 7 chars — decompiler must treat inner ids as derived, `origin_id`
   is the stable key.

## Authoring surface

```jsx
export const PriceCard = defineComponent(
  ({ plan, price, cta }) => ( … ),
  {
    title: 'Price Card',
    props: {
      plan:  { label: 'Plan name',  group: 'Content' },
      price: { label: 'Price',      group: 'Content' },
      cta:   { label: 'Button',     group: 'Actions' },
    },
  }
);
```
- Un-`defineComponent`ed functions keep today's inline expansion (zero breakage).
- `defineComponent` marks the function; invocation emits an instance node; the
  definition renders ONCE into a component tree.

## Props→overrides mapping (the core algorithm)

Render the component with defaults → tree A. For each declared prop, re-render
with a unique sentinel value → tree B; diff A/B to locate the exact
`(elementId, propKey)` the prop lands on. Wrap that setting in the `overridable`
envelope; record the registry entry (label/group/originValue). Constraints:
- A prop must resolve to EXACTLY ONE whole settings prop. Props that land in
  styles/classes (`tint`, `radius`, any sx-ish prop) are a **compile error** with
  a message explaining the Elementor constraint and the workaround (bake variants
  as separate components, or accept inline expansion for that component).
- Props landing on multiple elements: v1 = error; v2 candidate = fan-out to
  multiple overridable entries sharing one JSX prop (needs UX decision).
- Component-composing-component with prop forwarding emits the
  `overridable(override)` chain envelope (reference semantics: editor
  `resolve-overrides-chain`).

## Compile/bundle changes

- `runtime.mjs` (~line 64): registration seam — registered components render once
  per definition (uid = djb2 of normalized tree + title, reuse classes.mjs hasher);
  invocations emit instance nodes.
- `compile.mjs` `compileSite`: bundle gains
  `components: [{uid, title, elements, settings:{overridable_props}}]`.
- Build-time validation mirrors server 422s: atomic-only, no cycles, ≤100,
  unique titles/uids, override key consistency — fail at build with pointers.

## Deploy changes (`deploy.mjs`)

Phase order: variables → classes → **components** → pages.
1. `POST /elementor/v1/components` `status:'publish'` (batch). Map `{uid→id}`.
2. Rewrite instance nodes' `component_id` with real ids (bundles stay uid-keyed;
   ids are per-site).
3. Redeploy semantics: **there is no update-elements REST route.** v1 strategy:
   if a component with our uid exists and tree hash differs → create is not
   possible (duplicate uid) → update via the ultra-mcp path (below) or
   archive+recreate under a version-suffixed uid (drift!). DECISION REQUIRED
   (see Open questions) — recommended: ship the ultra-mcp component controller.
4. CSS priming: verify `/prime-css` covers component styles rendered via
   `Component_Styles` hooks after headless writes (test case, not assumption).

## ultra-mcp plugin extension (required for free-tier + updates)

`POST /components` requires ACTIVE Pro via Elementor's access controller. exjsx
targets free sites too. Add to elementor-ultra-mcp: a components controller
(pattern: existing controllers under includes/rest/, registered in
class-registrar.php) that calls `Components_Repository` directly — create,
update-elements (via `$document->save`), list-by-uid — gated by `manage_options`
+ the plugin's existing auth. This also solves the missing update route. Contract:
identical validation to Elementor's (reuse their validators — circular, atomic-only,
save-components) so behavior can't drift from native.

## Decompile changes

`decompile.mjs` (~line 221): intercept `widgetType === 'e-component'` before the
Raw fallback. Fetch component doc + overridable-props; decompile the tree once
into an exported `defineComponent` whose parameter names derive from override
labels; emit instances as `<PriceCard plan="Pro"/>` from `override` envelopes;
`overridable`-wrapped = prop forwarding. Inner hashed ids: ignore, key on origin_id.

## Test contract

Unit: registration seam (single render per definition), instance envelope
exactness (schema_source.id invariant), sentinel-diff prop mapping incl. failure
modes (style-prop error, multi-target error), cycle/atomic/limit build errors,
uid stability across builds, decompile round-trip (define → compile → decompile →
same JSX shape).
Integration (live, gated like existing :8947 suite): create+publish via both REST
paths, instance renders with overrides applied (screenshot), component edit
propagates to second page, redeploy-with-changes path, non-Pro site path via
ultra-mcp route, lock-status politeness check.

## Open questions (decide before implementation)

1. Update path: ultra-mcp controller (recommended) vs archive+recreate. Affects
   drift protection design.
2. Pro-tier UX: when deploying to a site WITHOUT ultra-mcp plugin and WITHOUT
   active Pro → fall back to inline expansion with a warning, or hard error?
   (Recommended: warn + inline-expand, keep builds portable.)
3. Multi-target props (one JSX prop → N elements): v2 fan-out design.
4. Style variants: document the "components can't have style props" constraint
   loudly in API card; consider `variant` prop pattern (N registered components)
   as the blessed idiom.
5. Cache invalidation of component CSS after headless writes (test may force a
   prime-css extension).
