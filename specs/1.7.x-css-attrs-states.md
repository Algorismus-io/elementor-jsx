# SPEC 1.7.x — custom_css completeness, attributes, style states

Status: SPECCED (source-verified, Elementor 4.2.1 free + ultra-mcp plugin).
Baseline surprise: custom_css emission ALREADY EXISTS in the kit (CUSTOM_CSS/css(),
and tw raw/hover:/focus: land as native custom_css). 1.7.x = close the gaps,
not build the feature.

## A. custom_css — close-out

Native contract (verified):
- Variant-level `custom_css: {raw: <base64 CSS declarations>}`, sibling of
  props/meta. Rendered VERBATIM inside the variant's selector block after
  resolved props → native CSS Nesting works (`&` = variant selector). Supported
  per-breakpoint AND per-state (state selector applied first, then media wrap).
- Sanitize on save: decode → `sanitize_textarea_field` → re-encode. DANGER:
  tag-like sequences get stripped (e.g. `<` in `content:"<"`).
- Core's base64 validation is a NO-OP (decode_string returns false, not null —
  the check never fires); the ultra-mcp validator's strict base64 gate
  (class-validator.php:673-687) is the only real guard. Keep relying on it.
- Renderer appends a literal `\n` two-char sequence — last declaration must end
  with `;`/`}`; kit's css() already guards this. Decompiled/imported foreign
  custom_css must be re-guarded.
- Document-settings `custom_css` is a DIFFERENT shape (plain string; the object
  shape fatals Pro sitewide) — already documented in kit; keep the lint.

Changes:
1. `css(n, decls, {breakpoint, state})` — add `state` targeting (today it only
   finds `state:null` variants); creates the `{breakpoint, state}` variant when
   absent. This unlocks per-state custom CSS (e.g. tablet-hover).
2. Compile-time lint: run the declarations through a sanitize-simulation and
   error when `sanitize_textarea_field` would mangle them (tag-like sequences);
   error on missing trailing `;`.
3. Decompile: invert variant custom_css → `css()`/`raw` faithfully incl. state.
Plugin: NO CHANGE NEEDED (verified pass-through with normalization on both the
documents and global-classes routes).

## B. attributes — ship storage, gate the promise

Native contract (verified):
- Envelope: `attributes: {$$type:'attributes', value:[{$$type:'key-value',
  value:{key:{$$type:'string',value},value:{$$type:'string',value}}}]}` —
  declared on effectively every atomic element schema.
- **CRITICAL: the DOM transformer is STUBBED in free 4.2.1** — PHP transformer
  returns null, editor JS returns ''. Attributes validate and persist but DO NOT
  reach the front-end DOM on this version. The wiring exists (before_render +
  twig macro consume a transformed string) — Elementor will flip it on.
- Core `esc_attr`s key+value; no attribute-name grammar validation.
- Unknown settings keys are stripped SILENTLY by core Props_Parser; the plugin
  has no settings-key truthfulness gate (it has one for style props).

Changes:
1. Kit: `ATTRS(obj)` helper (KV() already exists — one-liner) + `attributes`
   settings key in node().
2. JSX: `attrs={{'data-x': 'y'}}` prop on all intrinsic tags; types.d.ts
   `attrs?: Record<string,string>` following IntrinsicProps conventions.
3. Compile-time validation: attribute-name grammar; hard-block `class`, `id`,
   `style`, and `on*` (event handlers) — core won't.
4. **Version gate + honest docs**: API card states "stored & editor-validated on
   4.2.1; DOM emission depends on Elementor enabling its transformer — verified
   per-version by the certification suite." Certification suite gains an
   attributes-in-DOM probe so the moment Elementor un-stubs it, we flip the doc.
   Until then the runtime-carrier + `_cssid` remain the JS-hook path of record.
5. Plugin (recommended, small): add a settings-key truthfulness gate mirroring
   the style-prop gate, so misspelled keys error instead of vanishing.

## C. style states — native variants + tw completion

Native contract (verified):
- `variant.meta.state` ∈ {hover, active, focus, focus-visible, checked,
  e--selected, e--disabled, null}. Pseudo states render as `:state`; the two
  e-- states render as CLASS selectors (editor/tabs machinery toggles them).
- QUIRK: state `hover` renders as `:hover, :focus-visible` (comma pair, core's
  additional-states map). Accept and document; authored `focus-visible:` maps to
  its own meta.state.
- Native state variants already round-trip (kit's hover() proves it); plugin
  passes any core-valid state through.

Current exjsx: tw supports only `hover:`/`focus:` and compiles them to RAW
custom_css blocks (not native variants); sx has no state support; kit hover()
is the only native-variant emitter.

Changes (the core decision, resolved): SPLIT BY EXPRESSIBILITY —
- If every declaration in a state-prefixed tw utility maps to a schema prop →
  emit a NATIVE state variant (editor-visible in the state UI, schema-validated).
- Otherwise → fall back to the existing raw custom_css path (any CSS, invisible
  to the state UI). Deterministic, documented, best of both.
1. tw.mjs: extend prefix whitelist with `active:`, `focus-visible:`, `checked:`;
   keep `group-hover:`/`focus-within:`/`visited:` as raw-only (no meta.state
   equivalent) with clear errors; wire the split-by-expressibility emitter.
2. kit-components sx: `hover={{...}}`-style state objects accepted wherever sx
   is (styled/box), emitting native variants via the hover() mechanism
   generalized to all valid states (`stateVariant(node, state, props, bp?)`).
3. Decompile: state variants → state props / tw prefixes.
4. e--selected / e--disabled: expose in kit only (not tw) until a use-case shows
   up — they're editor-machinery classes.
